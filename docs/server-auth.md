# Server authentication rollout

Authentication uses the configured Supabase `users` table, never the browser's cached user list or the legacy performer directory. Only `admin_po`, `finance` and `super_admin` can sign in. `is_active=false` disables any account. Field performers remain selectable without app login. Existing plaintext PIN database storage is retained for compatibility; PINs are never included in session responses, grouped API user reads or client constants. Change known/default PINs in the protected database before rollout. This change does not rotate existing credentials automatically.

Required private server configuration:

- `AUTH_SESSION_SECRET`: a cryptographically random secret of at least 32 bytes (generate with `openssl rand -base64 48`). No fallback exists. Changing it invalidates all cookies.
- `AUTH_APP_ORIGIN`: exact canonical app origin including scheme, e.g. `https://your-host.example`. Local development needs its exact origin too, e.g. `http://localhost:3000`. Mutation requests require an `Origin` matching this configured origin; add no wildcard.
- Existing profile-specific Supabase URL and service-role key configuration. Keep the service-role key private. Configure the intended database profile explicitly.

Prepare/install `20261016000001_server_auth.sql` on the intended database through a reviewed rollout before switching login traffic. The migration only creates session and rate-limit state; it does not seed users or modify business records. Login fails closed if the tables or RPC are missing. Session cookies are signed, HttpOnly, SameSite=Strict and Secure in production, with an eight-hour expiry. Each authenticated request checks the stored session and the current DB identity. Logout revokes the stored session; account PIN, role or active-state changes invalidate existing sessions. Session records contain keyed credential fingerprints, never PINs.

The atomic database login limiter allows ten attempts per fifteen minutes. On Vercel it partitions on the platform's `x-vercel-forwarded-for`; on other hosts it intentionally shares one conservative bucket rather than trusting a client-supplied forwarding header. Configure any deployment-specific trusted proxy partitioning explicitly before increasing limits. Old session/rate-limit rows may be pruned by an administrator after expiry; no automated pruning is installed.

Deploy the authenticated `/api/tukar-faktur` and `/api/accounting/vendor-bill-number` bridges together with the migrated callers. Then apply `20261016000005_rpc_access.sql` to revoke anonymous/authenticated execution of privileged financial, goods and TF RPCs and grant execution only to `service_role`. This migration also enforces Draft state under the TF transaction lock and preserves published batches. These files are prepared locally and have not been applied to the live database. Run privilege checks on the intended target during rollout; applying application code alone does not remove existing database RPC grants.

API maintenance requires Super Admin. Generic table writes use explicit role allowlists; direct GL/cash/session-table writes and historical business deletes are rejected. Existing invoice commercial snapshots and settlement fields, AP settlement fields and bank balances cannot be overwritten through generic writes. The atomic transaction APIs own those fields. Goods, purchasing and financial events post through their authenticated source commands. The old standalone journal/cash endpoints now return 410 after authentication; no business flow may post their individual legs. Money movement remains Finance/Super Admin only. Existing user edits preserve the private PIN; active office PINs have an atomic unique index. Field performers use non-login identifiers and need an explicit numeric PIN if promoted to an office account.

For other API handlers import `requireApiUser(request, allowedRoles?)` and `apiAuthResponse(error)` from `@/lib/api-auth`. The former returns the fresh, PIN-free `User`, throwing on failure. The latter returns a failure `Response` for an auth error or `null` for another error. The global API proxy guards all API paths as an additional boundary, but handlers must retain explicit guards for direct calls and their own role requirements.
